# Command Pipeline Contract

This document defines the command boundary used by EdgeHome Harness. It is the
source of truth for what the model may emit, what Rust must validate, and where
backend-specific payloads are allowed to appear.

## Summary

```text
MiniCPM proposes a backend-neutral candidate JSON.
Rust validates and normalizes it into an internal command.
The gate and planner produce an ExecutionPlan.
Backend adapters translate the verified plan into backend-specific payloads.
```

The model output is never a command and is never executed directly.

## Layers

| Layer | Type | Owner | Trust level |
| --- | --- | --- | --- |
| Candidate JSON | `ModelCandidate` | MiniCPM / MockModel | Untrusted |
| Internal command | `NormalizedCommand` | Rust Harness | Must be resolved and gated |
| Verified plan | `ExecutionPlan` | Gate + planner | Trusted dry-run boundary |
| Backend payload | `DryRunPlan.payload` | Backend adapter | Backend-specific |

## Layer 1: ModelCandidate

`ModelCandidate` is the only JSON contract the model is asked to produce.

It is backend-neutral and should remain small:

```json
{
  "schema_version": "model_output.v1",
  "intent": "control_device",
  "room": "living_room",
  "device_alias": "living room light",
  "device_type": "light",
  "action": "turn_on",
  "params": {}
}
```

The model must not emit backend routing fields such as:

```text
Home Assistant entity_id
MIoT did / siid / piid / aiid
Matter node / endpoint / cluster
MQTT topic
tokens
backend URLs
vendor API payloads
```

## Layer 2: NormalizedCommand

`NormalizedCommand` is an internal command shape owned by Rust.

It may contain a resolved `device_id`, but that identifier must come from a
registry or memory resolver, not from vendor payload generated by the model.

Before a command can enter the policy gate, it must satisfy:

```text
known intent
known room
known device type
known action
known risk
resolved device_id
valid command params
```

## Layer 3: ExecutionPlan

`ExecutionPlan` is backend-neutral. It describes what the harness intends to do
after schema validation, device resolution, capability validation, and policy
gating.

It should not contain:

```text
Home Assistant entity_id
MQTT topic
MIoT service/property IDs
Matter cluster IDs
tokens
URLs
```

Those fields belong to adapter configuration and adapter output.

## Layer 4: Backend Payload

Backend payloads are generated by adapters after the plan has been verified.

Examples:

```text
MockAdapter -> deterministic mock payload
HomeAssistantAdapter -> Home Assistant service-call payload
Future MqttAdapter -> MQTT topic and payload
Future MiotAdapter -> MIoT property/action payload
Future MatterAdapter -> Matter command route
```

Unimplemented backends must fail closed. They must not fall back to mock payloads.

## Required Invariants

```text
ModelOutput != Command
ModelCandidate is backend-neutral
NormalizedCommand is internal
ExecutionPlan is backend-neutral
DryRunPlan.payload is backend-specific
Vendor identifiers live in registry or adapter config
Unimplemented backends fail closed
```

## Why This Matters

Letting a small model emit vendor payloads directly would make the system
fragile:

```text
The model may hallucinate entity IDs or topics.
Prompts would become vendor-specific and hard to validate.
Tokens or private routes could leak into model context.
Rust would lose a clear safety boundary.
```

EdgeHome Harness keeps the model contract fixed and moves customization to
registry and adapter layers.
