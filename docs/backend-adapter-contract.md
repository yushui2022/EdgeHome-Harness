# Backend Adapter Contract

This document defines how backend adapters should translate a verified
`ExecutionPlan` into backend-specific payloads.

The adapter layer is the only place where vendor-specific routing fields may
appear.

## Current Status

| Backend | Status | Behavior |
| --- | --- | --- |
| Mock | Implemented | Produces deterministic dry-run payloads |
| Home Assistant | Demo adapter implemented | Produces service-call dry-run payloads |
| MIoT / Xiaomi | Future target | Fails closed today |
| Matter | Future target | Not represented as an implemented backend today |
| MQTT | Future target | Fails closed today |

## Adapter Inputs

A backend adapter may read:

```text
DeviceRecord
NormalizedCommand
ExecutionPlan
AdapterProfile, when implemented
```

It must not read:

```text
raw user text
raw model output
unvalidated JSON
tokens from model context
vendor IDs generated by the model
```

## Rust Trait Shape

The executor crate exposes the adapter boundary as:

```rust
pub trait BackendAdapter {
    fn kind(&self) -> BackendKind;

    fn dry_run_payload(
        &self,
        device: &DeviceRecord,
        command: &NormalizedCommand,
        plan: &ExecutionPlan,
    ) -> ExecutorResult<Value>;
}
```

Implemented adapters:

```text
MockAdapter
HomeAssistantAdapter
```

Unsupported backend kinds must return a clear error:

```text
backend adapter is not implemented: mqtt
backend adapter is not implemented: miio_local
```

## Adapter Rules

Adapters must:

```text
Use only verified internal types.
Read backend routes from registry or adapter profile config.
Generate backend-specific dry-run payloads deterministically.
Fail closed when a route or backend is missing.
Avoid leaking tokens into traces or model prompts.
Keep real execution disabled by default.
```

Adapters must not:

```text
Trust model-provided vendor IDs.
Call real devices during dry-run planning.
Silently fall back to mock payloads for unsupported backends.
Infer hidden backend routes from natural language.
Store secrets in docs, configs, or traces.
```

## Current Test Coverage

The executor crate pins the current adapter behavior with golden and
fail-closed tests:

```text
Mock supported action -> exact dry-run payload
Home Assistant light.turn_on -> exact dry-run payload
Home Assistant light brightness -> exact dry-run payload
Home Assistant climate temperature -> exact dry-run payload
Home Assistant climate mode -> exact service-call payload
Missing Home Assistant route -> fail closed
Invalid Home Assistant entity_id -> fail closed
MQTT selected -> BackendAdapterNotImplemented
MiioLocal selected -> BackendAdapterNotImplemented
Home Assistant dry-run -> no token required and no real service call
Dry-run payload serialization -> no token/env secret leakage
Real Home Assistant execute -> disabled by default
```

These tests are deliberately about adapter boundaries. They do not claim full
Home Assistant coverage or real-device production support.

## Mock Adapter

The mock adapter is the deterministic test and demo baseline.

Example payload:

```json
{
  "backend": "mock",
  "device_id": "hallway_light",
  "backend_entity_id": "mock.light.hallway",
  "room": "hallway",
  "device_type": "light",
  "action": "turn_on",
  "operation": "set_power_on",
  "params": {}
}
```

The mock adapter is not real device control.

## Home Assistant Adapter

The Home Assistant adapter maps an `ExecutionPlan` to a service-call payload.

Example payload:

```json
{
  "backend": "home_assistant",
  "device_id": "hallway_light",
  "entity_id": "light.hallway",
  "service": "light.turn_on",
  "service_path": "/api/services/light/turn_on",
  "payload": {
    "entity_id": "light.hallway"
  }
}
```

`entity_id` comes from `DeviceRecord.backend_entity_id`. It is not emitted by
MiniCPM.

## Future MQTT Adapter

MQTT is a publish/subscribe protocol. It does not define a universal smart-home
JSON format.

A future adapter profile should define:

```text
topic
payload template
QoS, if needed
retain, if needed
```

Example design only:

```yaml
backend: mqtt
status: future_design_only
routes:
  - device_id: hallway_light
    action: turn_on
    topic: home/hallway/light/set
    payload:
      power: "on"
```

## Future MIoT Adapter

MIoT devices commonly require IDs such as:

```text
did
siid
piid
aiid
```

A future MIoT adapter must read those values from an adapter profile or secure
device registry extension. The model must not emit them.

Example design only:

```yaml
backend: miot
status: future_design_only
routes:
  - device_id: bedroom_air_conditioner
    action: set_temperature
    method: set_properties
    did_env: EDGEHOME_MIOT_BEDROOM_AC_DID
    siid: 2
    piid: 6
```

## Future Matter Adapter

Matter is not a JSON payload format. A future Matter adapter would need a
controller and a route model for:

```text
node
endpoint
cluster
attribute
command
```

Until that exists in code and tests, Matter must remain a future adapter target.

## Minimum Tests For Any New Adapter

Any new adapter must include golden tests for:

```text
supported action -> expected payload
missing route -> fail closed
unsupported action -> fail closed
no token or secret leakage
dry-run does not execute real device calls
```

Only after those tests pass should README language move from "future target" to
"implemented".
